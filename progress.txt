## Pre-existing Learnings (from v1 + design conversation)

- This is a Next.js 16 + Supabase + Tailwind 4 app. Single-user, no auth. RLS is on but permissive.
- Supabase client is accessed exclusively via `getSupabase()` from `src/lib/supabase.ts`. Don't create new clients.
- Demo mode is real and important — `NEXT_PUBLIC_DEMO_MODE=true` swaps to a mock client in `src/lib/supabaseDemo.ts`. Both code paths must work end-to-end. If a query is added in real Supabase, the demo client must handle it too.
- Types flow from `src/types/database.ts`. It is the single source of truth for table shapes. Update this FIRST when changing schema.
- v1 schema had `clients` / `projects` / `time_entries`. v2 schema has `trails` / `projects` / `rates` / `time_entries`. The `projects` table is re-parented from `client_id` to `trail_id`.
- Migration is DESTRUCTIVE — drop v1 tables, create v2 tables. Davis has confirmed no production data to preserve. Don't try to migrate data across.
- Ralph WRITES the migration SQL but does NOT execute it. Davis runs migrations manually in Supabase SQL Editor after this run completes.
- Rates are time-versioned. A rate row is immutable once inserted. To "change" a rate, insert a new row with new `effective_from` AND update the previous row's `effective_until`.
- The trail `kind` enum is exactly: `client`, `employer`, `personal`, `project`. No others.
- Time entries no longer carry rate. Cost is computed at query/display time via `src/lib/rates.ts`.
- `time_entries.notes` is now semantically "invoice line description only" — not a general capture field. Capture will live in observations (run #2).
- `time_entries.source_observation_id` is a UUID column with NO FK constraint yet. The `observations` table doesn't exist until run #2.

- Do NOT try to preserve v1 data through the schema reset. The migration is destructive by design.
- Do NOT create a separate `clients` concept alongside trails. Clients are just trails with `kind='client'`.
- Do NOT add a rate column to `time_entries`. Rates live in the `rates` table only.
- Do NOT UPDATE a rate row in place. Always insert a new one.
- Do NOT refactor unrelated code "while you're in there." Stay focused on the task list.
- Do NOT build journal, observation, briefing, or open-loop features in this run. They are explicitly out of scope.
- Do NOT introduce new state libraries (Zustand, Redux, etc.). The existing React-state + Supabase pattern stays.

## Learnings

### Task 1 — Migration SQL
- The `update_updated_at_column()` trigger function is re-created with `CREATE OR REPLACE` to be idempotent (safe if 001 already ran it).
- No trigger on `rates` table by design — rate rows are immutable; changes = new INSERT, not UPDATE.
- `DROP TABLE IF EXISTS ... CASCADE` drops child FK rows cleanly without needing to order drops by dependency.
- The comment line "-- STEP 4: CREATE INDEXES" contains "CREATE INDEX" text and inflates grep -c counts by 1; actual index count was 8 as specified.
